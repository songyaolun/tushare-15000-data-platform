# 架构说明

平台以接口总账为入口，将公开文档中的权益事实、采集政策、运行证据和实际消费关联起来。15,000 积分表示权限与频率档位，平台按业务需要采集，不制造请求。

```mermaid
flowchart LR
    D[公开文档与离线快照] --> C[接口总账与政策]
    C --> P[任务计划]
    P --> R[传输与原始层]
    R --> Q[标准化与质量门禁]
    Q --> S[标准版本与检查点事务]
    S --> I[时点信息产品]
    I --> V[覆盖率与债务]
```

## 存储边界

DuckDB 使用单线程、512 MiB 内存限制，适合个人账户的单写者工作负载。控制表保存接口、任务、探活、检查点、质量结果和消费清单。标准层按接口、业务键、版本和证据来源隔离，保留所有观察版本，包含 A→B→A 的历史修订。

`products.duckdb` 与控制库、`reference.duckdb` 分离。`product` schema 保存 11 张共享产品表，`research` schema 保存六个股票业务产品的结果、特征、贡献、证据、门禁、信号、血缘及运行摘要，其中 P03 为统一右侧候选榜。参考输入只读，产品记录按模型、版本、单位和时点验证。详见[产品加工基础层](产品加工基础层.md)与[股票研究闭环](股票研究闭环.md)。

原始 JSON 按内容哈希保存。请求标识仅包含接口名与无凭据参数。成功响应先原子落盘、同步并读回校验，再解析字段。分页、标准化或质量检查失败时，保留已有原始文件，标准数据和水位不提交。标准层和检查点在同一事务中提交；已登记计划中的早期失败分片会阻止水位越过缺口。

已提交任务重复执行不会请求数据。新的回看计划具有新的观察时点，可获取迟到记录与修订。原始文件和数据库不组成跨资源事务：崩溃可能留下没有对应检查点的原始文件，这是可恢复的预期状态。不会根据孤立原始文件推断采集成功。

## 时间语义

报告期、公告日期、实际披露日期、生效时间和系统观察时间各自保存。财务记录保留 report_type、update_flag 和源版本。as-of 同时检查业务可见时间和 observed_at；后观察到的旧公告修订不会泄漏给更早的查询。

没有可信披露时点的快照只允许在本系统观察之后使用。月、季、年保持报告期间含义，不伪造发布日期。日粒度公告按 UTC 日末可见，属于保守边界；若需要国内市场盘中回测，应补充精确披露时间与明确交易时区。

上述 UTC 日末规则属于旧 `pit.as_of`。新产品基础层对日期级公告使用显式来源市场时区的次日零点，并区分观察后可见与已经生效；历史 PIT 资格仍为 false，不启用历史交易结论。

未复权价格和复权因子分别保存。qfq 和 hfq 都要求调用方显式提供固定锚点，计算为价格乘当日因子再除以锚点因子。平台不会只保留随时间变化的前复权序列。

## 覆盖率口径

登记覆盖率以全部发现记录为分母。探活、采集、消费、新鲜度和回填按各自运行证据统计，输出分子、分母；没有计划的历史回填率为 null。消费要求真正生成包含数据的产物，仅配置一个产品名不会计作已消费。

离线 fixture 与 live 分开记录。离线全部通过也不能证明真实账户权限。官方文档冲突、未归类接口、缺少更新时间、质量参考数据缺失、尚未采集或消费均保留为债务。历史回填指标只覆盖已登记计划范围，不代表已覆盖提供方全部历史。

文档分类与账户实测独立存储。公共只读接口不因文档待复核、权限未知、独立权限或停更标签而停止探测；同账户、同政策的最新成功证据可以放行真实采集。质量门禁继续阻止不完整标准数据提交。扫描样本保留原始数据和质量诊断，不计作完整历史采集。数据库按公开账户别名隔离，使用者更换实际账户时必须同时更换别名及数据库。
