# 全产品离线研究

`research-all` 把权威矩阵中的 206 个接口分配给十三个默认业务产品。原 `research` 命令仍用于 P01、P03、P04、P06、P07、P13 六个默认股票产品。全产品入口复用它们的业务构造器和消费逻辑，并增加七个跨资产产品。P03已统一为右侧交易候选，旧周期榜不再执行。基础层的接口覆盖记录不计作业务消费。

面向使用者的产品用途、产物和组合方法集中在[产品说明书](产品说明书.md)。本文继续说明运行、审计、性能和正式验收细节。

## 产品与接口归属

| 产品 | 接口数 | 结果内容 |
| --- | ---: | --- |
| P02 | 22 | 主题状态、成员广度、动量、资金确认、拥挤与成员贡献 |
| P05 | 7 | 公告可见的预期区间、修正、兑现差异与证据链 |
| P08 | 18 | ETF 本体、成分暴露、重合、流动性、跟踪与份额变化 |
| P09 | 19 | 商品状态、期限结构、仓单和持仓压力、企业关系证据 |
| P10 | 26 | 跨市场状态、汇率与利率冲击、明确的可比关系 |
| P11 | 14 | 融资压力、报价与成交流动性、期权及尾部风险 |
| P12 | 1 | 显式持仓或基金披露股票部分的组合诊断 |
| 原六产品 | 99 | 市场、候选、基本面、治理、资金和事件研究 |

接口主归属、用途和使用字段以 `src/tushare_entitlement_hub/data/product_consumers.csv` 为准。七产品的 `API_FIELDS` 在运行前与矩阵逐项核对。相同代码不能自动建立跨市场实体关系；缺少实体、币种、单位、公开时间或可比关系证据时，相关指标保持 `unknown`。

## 从参考库生成结果

先在本地将参考库路径、输出目录与截止时间赋给下列变量。输出目录应与参考库独立，不能覆盖原参考库。命令中的值是示例，请使用本地正式验收所选的参考库和研究时点。

```bash
REFERENCE=/path/to/reference.duckdb
PRODUCT_OUTPUT=/path/to/all-products.duckdb
PRODUCT_CONFIG=/path/to/all-products-config.json
PRODUCT_AUDIT=/path/to/all-products-config.audit.json
ANALYSIS_AS_OF=2026-10-04T12:00:00Z

uv run tushare-hub research-all build-config \
  --reference "$REFERENCE" --output "$PRODUCT_CONFIG" \
  --audit "$PRODUCT_AUDIT" --as-of "$ANALYSIS_AS_OF"

uv run tushare-hub research-all run \
  --reference "$REFERENCE" --output "$PRODUCT_OUTPUT" \
  --config "$PRODUCT_CONFIG" --as-of "$ANALYSIS_AS_OF"

uv run tushare-hub research-all validate \
  --reference "$REFERENCE" --output "$PRODUCT_OUTPUT"
```

`build-config` 只读参考库，检查来源清单的存在性、唯一性和契约指纹，完整分批认证单位。额外的合法目录项不会导致失败。默认单源扫描上限为 200 万行、全部来源扫描上限为 500 万行，跨市场主数据实体上限为 50 万个。生成配置会固化前两个运行时行数边界，避免构建阶段通过全量扫描后，执行阶段又退回旧股票研究的 32,768／131,072 行默认值。若正式参考库超出预算，先核对实际行数或去重实体数，再显式传入 `--maximum-source-rows`、`--maximum-total-rows` 或 `--maximum-entities`。不得提高 DuckDB 内存或单结果上限来掩盖缺口。构建失败时，标准输出仅包含固定 `detail_code`，不回显来源载荷。

`run` 的退出码为：完整结果 `0`，存在明确缺口的结果 `2`，执行失败 `1`。退出码 `2` 的结果已经完成原子发布，可以继续执行 `validate`。`validate` 成功为 `0`，失败为 `1`；`valid=true` 只证明存储、引用、确定性重算和配置契约一致，不代表数据齐备、历史 PIT 合格或策略有效。

需要分产品运行时，在 `run` 后增加 `--product P05` 等选项，可重复指定。P03 和 P13 会展开 P04、P06、P07 依赖；P12 只展开原有十三个默认产品。相同参考文件、配置、持仓、产品闭包和预算会得到相同运行标识，重复运行会校验已有结果后复用。

三套排名可以一次生成，但结果拥有不同的 `product_id`、因子、门禁、分数和名次，不是旧 P03 的三个标签：

```bash
uv run tushare-hub research-all run \
  --reference "$REFERENCE" --output "$PRODUCT_OUTPUT" \
  --config "$PRODUCT_CONFIG" --as-of "$ANALYSIS_AS_OF" \
  --product P03
```

统一P03要求完整、已认证的61日观察窗口，识别回调、低点抬高、突破或回踩确认，再约束入场距离与历史阻力空间；过去涨幅不直接评分。规则详见[P03右侧交易候选](P03右侧交易候选.md)。

## 读取结果和定位缺口

```bash
uv run tushare-hub research-all results --output "$PRODUCT_OUTPUT" --product P02 --limit 20
uv run tushare-hub research-all results --output "$PRODUCT_OUTPUT" --product P05 --limit 20
uv run tushare-hub research-all results --output "$PRODUCT_OUTPUT" --product P08 --limit 20
uv run tushare-hub research-all results --output "$PRODUCT_OUTPUT" --product P09 --limit 20
uv run tushare-hub research-all results --output "$PRODUCT_OUTPUT" --product P10 --limit 20
uv run tushare-hub research-all results --output "$PRODUCT_OUTPUT" --product P11 --limit 20
uv run tushare-hub research-all results --output "$PRODUCT_OUTPUT" --product P12 --limit 20
uv run tushare-hub research-all results --output "$PRODUCT_OUTPUT" --product P03 --limit 20
uv run tushare-hub research-all audit --output "$PRODUCT_OUTPUT"
```

结果采用统一信封、指标、贡献、证据、门禁、信号和血缘七表。`results` 逐条输出 JSONL，单次最多 512 条。`audit` 返回逐接口状态和原因计数。

| 状态 | 判断依据 |
| --- | --- |
| registered | 权威矩阵中的接口具有唯一消费登记和可解析处理器 |
| assigned | 本次产品依赖闭包包含该接口的主产品 |
| executed | 主产品真实处理器已执行，并产出业务结果或结构化降级结果 |
| readable | 参考表、来源清单和质量契约允许读取 |
| configured | 配置为该来源提供相应绑定规则 |
| observed | 可用指标或通过的门禁实际使用了本来源通过实体、时间、单位和质量门禁的字段；旧产品还须通过原消费状态认证 |
| unresolved | 存在需说明的数据、配置、关系、单位或消费缺口 |

`observed` 与 `unresolved` 可同时为真。单个接口有可认证记录，不代表所有记录和字段均已可用。引用去重使用磁盘键表，同一来源行被多个结果引用不会重复计入 `observed_rows`。原六产品还必须通过原消费状态认证，不能仅靠新的审计计数提高 observed。

`consumption_reason_counts` 单独列出业务消费原因，并合并到 `reason_counts`。新产品的未知指标和未知门禁，只向其实际引用的本产品接口归因；同一诊断内重复接口和重复原因码去重，独立诊断分别计数。无引用的产品级缺口、仅引用其他产品的缺口、已知为假的门禁和不适用指标，不会被当作本接口的未知业务原因。`reason_counts` 汇总输入、绑定及消费诊断的出现次数，不能用作独立坏行数量。

成员有效期缺失时只说明观察快照。报告期与公开时间分别保存，后者缺失不得由报告期替代。报价和成交分开；普通接口与 VIP 或其他重复来源只做核对，不叠加经济量。来源内的序列身份只支持来源内部研究，不能冒充已认证证券生命周期或跨来源关系。

同一接口混有多种币种时，全列配置不假定统一币种。新绑定审计可显式授权逐行币种认证：仅使用本行明确币种和已证明单位生成证书，并把该授权纳入配置指纹。币种明确仍不能补救文档明确未知的单位。期货与期权的“手”只在契约、原单位和标准单位一致时原样用于合约内数量计算，不换算成股票股数或跨品种实物数量。

字段的数值语义由共享标准层判定。文档类型为文本但明确声明了百分比等受支持单位时，新参考库采用数值列；旧参考库中的规范数值文本，只在来源单位与标准单位均一致时恢复为数字，不再次按来源单位缩放。消费审计对这类字段同样要求事实证书。读入投影保留显式绑定的实体键，不能因该键未出现在业务指标字段中而丢弃。

`rt_hk_k` 和 `stock_company` 的契约只支持当前来源快照。缺业务日期时可以保留来源内部的观察和证据，数据日期仍为空；不据此认证证券历史身份、实时收益或历史 PIT。

## 显式持仓输入

持仓文件是 JSON 数组，每项包含 `entity_type`、`entity_id`、`as_of`、`weight`。权重使用 0 至 1 的比例，总和须为 1；同一实体不能重复。可选 `portfolio_id` 和 `currency` 只保留其声明语义，不推测换汇关系。

```json
[
  {
    "entity_type": "security",
    "entity_id": "cn:security:EXAMPLE:listed",
    "as_of": "2026-10-04T12:00:00Z",
    "weight": 1.0,
    "portfolio_id": "example_portfolio",
    "currency": "CNY"
  }
]
```

上述实体仅为格式示例，实际输入须使用配置和结果中的真实实体标识。运行时添加 `--holdings /path/to/holdings.json`。缺少持仓时输出 `input_required`；基金持仓只覆盖已披露的股票部分，未披露资产保持未知。所有产品均不读取券商账户、不生成自动下单指令。

基金披露可见但权重、持仓实体或父结果不可信时，仍输出 `input_required`，并按来源记录标识保留最多八行确定性证据。未知门禁的引用用于追查缺口，不能将该接口升级为 observed；未来或隔离披露不会进入这组证据。

`parent_multiset_sha256` 覆盖实际落库父结果的完整规范化表示，包括消费审计信息。可按 `parent_result_ids` 读取父结果，逐项计算 SHA-256，将整数摘要相加后对 `2**256` 取模复算。

显式用户持仓优先于基金披露。选择显式持仓时，只保留这些持仓实体的父结果，其他基金披露不会占用父结果预算；未执行 P12 时不解析基金持仓关系。

P12 输出 HHI、最大及前五持仓权重、资产类型暴露，以及同名同单位上游比例指标的加权值。父指标缺失或存在多个候选时不填零。基金市值仅在全部使用记录的金额和币种可比时求和。清算天数缺少组合资金规模与参与率时保持未知；价格下跌 20% 的输出只是明确假设的情景，不是预测。持仓明细展示前 32 项，证据展示前 8 项，完整持仓和父结果仍由摘要与血缘覆盖。

## 性能与发布边界

DuckDB 固定为单线程、512MB。执行器按产品所有权加载 206 个来源，产品完成后释放上下文；只跨产品复用 `daily`、`daily_basic`、`index_daily`、`stk_limit`、`suspend_d` 五个明确旁证来源，不再让全部 99 个股票来源或 107 个跨资产来源同时常驻。所有来源仍共享配置中的总保留行数预算。新增来源的单产品保留字节预算为 256MiB、单源 128MiB、单投影行 64KiB；达到容量限制时整组降级，不能用截断集合生成精确总量。当前目录型主数据只保留截止时点仍生效的实体，历史原始记录仍完整保存在参考库中。

新增输入按实体和业务期间分桶保留。`daily` 保留最近 61 个观察期；六类利润表、资产负债表、现金流量表和 `fina_audit` 各保留最近 12 期；其他普通来源保留最新两个完整期间，公告版本类保留有界的全部版本。`disclosure_date` 只保留每个实体最近两个报告期、期间内版本完整保留，完整历史仍在参考库中可审计。行数与字节数随新增、淘汰增量更新，避免每加入一行就重新扫描整组。最终按来源记录标识排序，保持确定性输出。

结果数量默认上限为 10 万，可通过 `--maximum-results` 设置。单结果 JSON 保持 8MiB 硬门禁，在该结果的 SQL 写入前拒绝超限。运行的物理 JSON 总预算默认 32GiB，组合父结果预算为 2 万条，可通过 Python `RunLimits` 显式设定。累计预算在写入进度点和写入完成时检查，超限的私有副本不会发布。

存储复用分区、128 行或 512KiB 插入批、16MiB 分段事务及磁盘唯一键登记。所有写入先进入 staging 副本，关闭连接后重新打开，核对结果重建、七表投影、跨段唯一键与父引用，全部通过才原子替换目标文件。失败清理副本并保留已有产品库；并发写入仍由共享 staging 锁和发布版本检查保护。

分区键校验由 DuckDB 一次扫描后按 `hash(record_id) % 256` 写入临时桶。每个桶按完整的 `record_id`、`run_id`、`result_id` 三元组排序并逐项比较，不用哈希值代替内容相等，也不把数百万条键逐行搬入 SQLite 删除。临时桶随校验结束清理。正式库的七表键校验在 512MB DuckDB 限制下完成，其中最大的 `lineage` 表有 3,889,661 行；七表合计校验耗时 129.767 秒。

常规 CI 跳过标记为 `resource_intensive` 的生产规模压力用例，避免超过平台两小时作业时限；其余测试仍执行 100% 覆盖门禁。完整压力验收使用 `uv run pytest -m resource_intensive` 单独运行，本轮已完成数百万投影、宽结果、事件父结果和 staging 发布场景。

`validate` 会重算当前参考指纹对应的全产品批次，核对逐表摘要与消费摘要。旧批次没有对应历史参考文件时，只能验证库内完整性，不能声称完成历史来源重算。生成的配置、DuckDB、JSONL、原始行情和缓存均不应提交到 Git。
